Q1. What is the difference between var, let, and const? [L1]
Answer: var is function-scoped and can be redeclared/reassigned, it's also hoisted with undefined.
let is block-scoped, can be reassigned but not redeclared in the same scope. const is block-scoped
andcannotbereassignedafterinitialization(thoughobjectpropertiescanstillbemutated).Inmodern
JavaScript, const is preferred by default, let when reassignment is needed, and var is generally
avoided due to its scoping quirks.
Q2. What are the primitive data types in JavaScript? [L1]
Answer: JavaScript has 7 primitive types: string, number, boolean, null, undefined, symbol (ES6),
and bigint (ES2020). Primitives are immutable and compared by value. Everything else in JavaScript
is an object, including arrays, functions, and dates. Understanding primitives is crucial because they
behave differently from objects in terms of comparison, copying, and memory.
Q3. What is the difference between == and ===? [L1]
Answer: == is the loose equality operator that performs type coercion before comparison, so '5' == 5
returns true. === is the strict equality operator that compares both value and type without coercion,
so '5' === 5 returns false. Best practice is to always use === to avoid unexpected type coercion bugs.
The only common exception is checking for null or undefined with == null.
Q4. What is an arrow function and how does it differ from a regular function? [L1]
Answer: Arrow functions (=>) provide a shorter syntax for writing functions. Key differences: they
don't have their own 'this' binding (they inherit from the enclosing scope), they can't be used as
constructors, they don't have the 'arguments' object, and they can't be used as generator functions.
Arrow functions are ideal for callbacks and methods that don't need their own 'this' context.
Q5. Explain destructuring and provide examples with objects and arrays. [L2]
Answer: Destructuring extracts values from objects/arrays into distinct variables. For objects: const
{ name, age } = person extracts name and age properties. For arrays: const [first, second] = arr
extracts by position. You can set defaults ({ name = 'Unknown' } = {}), rename variables ({ name:
userName } = person), and use rest patterns ({ a, ...rest } = obj). Destructuring is commonly used in
function parameters and import statements.
Q6. What is the spread operator and what are its common use cases? [L2]
Answer: The spread operator (...) expands iterables into individual elements. Common uses include:
copying arrays ([...arr]), merging arrays ([...arr1, ...arr2]), copying objects ({...obj}), merging objects
({...obj1, ...obj2}), and passing array elements as function arguments (Math.max(...numbers)). For
objects, later properties override earlier ones during merging. It creates shallow copies, so nested
objects are still referenced.
Q7. What are template literals and tagged templates? [L2]
Answer: Template literals use backticks and allow embedded expressions (${expression}), multi-line
strings, and string interpolation. Tagged templates are an advanced feature where a function
processes the template literal: tagFunction`Hello ${name}`. The tag function receives an array of
string parts and the interpolated values separately, enabling custom string processing like
sanitization, localization, or DSLs like styled-components' CSS-in-JS.
Q8. Explain the difference between map, filter, and reduce array methods. [L2]
Answer: map() transforms each element and returns a new array of the same length. filter() returns a
new array with only elements that pass a test condition. reduce() accumulates array elements into a
single value using an accumulator. Examples: [1,2,3].map(x => x*2) gives [2,4,6]; [1,2,3].filter(x =>
x>1) gives [2,3]; [1,2,3].reduce((acc,x) => acc+x, 0) gives 6. These methods don't mutate the original

Q9. Explain closures with a practical example of when you'd use one. [L3]
Answer: A closure is a function that retains access to its lexical scope even when executed outside
that scope. Practical uses include: data privacy (creating private variables), function factories, and
maintaining state in callbacks. Example: function createCounter() { let count = 0; return () => +
+count; } - the returned function 'closes over' count, keeping it private. Closures are fundamental to
patterns like module pattern, currying, and event handlers that need to remember context.
Q10. What is the event loop and how does JavaScript handle asynchronous
operations? [L3]
Answer: The event loop is JavaScript's concurrency model. It continuously checks the call stack and
task queues. When the stack is empty, it processes the microtask queue (Promises, queueMicrotask)
completely, then takes one task from the macrotask queue (setTimeout, I/O). This explains why
Promise.then() runs before setTimeout(..., 0). Understanding this is crucial for predicting execution
order and avoiding blocking the main thread in Node.js or browsers.
Q11. What are Promises and how do async/await relate to them? [L3]
Answer: Promises represent eventual completion/failure of async operations with states: pending,
fulfilled, or rejected. They support chaining with .then()/.catch()/.finally(). async/await is syntactic
sugar over Promises - async functions always return Promises, and await pauses execution until a
Promise resolves. Error handling uses try/catch with async/await. Key gotcha: await only pauses the
async function, not the caller, and forgetting to await is a common bug that leads to unhandled
promises.
Q12. Explain 'this' keyword behavior in different contexts. [L3]
Answer: 'this' depends on how a function is called: in a method, it's the object; in a regular function
(non-strict), it's global/window; in strict mode, it's undefined; in arrow functions, it's inherited from
enclosingscope;withnew,it'sthenewinstance;withcall/apply/bind,it'sexplicitlyset.Commonpitfall:
losing 'this' in callbacks. Solutions include arrow functions, bind(), or storing 'this' in a variable.
Understanding 'this' is essential for working with classes and object-oriented patterns.
Q13. Explain prototypal inheritance and how it differs from classical inheritance. [L4]
Answer: JavaScript uses prototypal inheritance where objects inherit directly from other objects via
the prototype chain. Every object has an internal [[Prototype]] link. When accessing a property, JS
walks up the chain until found or reaching null. Unlike classical inheritance (classes as blueprints),
prototypes are live objects - changes affect all inheriting objects. ES6 classes are syntactic sugar
over prototypes. Object.create() creates objects with specific prototypes. Understanding this explains
how methods are shared, instanceof works, and how to properly extend built-ins.
Q14. What are generators and iterators? When would you use them? [L4]
Answer: Iterators are objects with a next() method returning {value, done}. Generators (function*) are
functions that can pause execution with yield and resume later, automatically implementing the
iterator protocol. Use cases: lazy evaluation of large/infinite sequences, implementing custom
iterables, simplifying async flow with co/redux-saga, processing streams, and creating state
machines. for...of loops consume iterators. Generators maintain their context between calls, enabling
elegant solutions for pagination, tree traversal, or chunked processing.
Q15. Explain WeakMap and WeakSet. When would you use them over regular Map/
Set? [L4]
Answer: WeakMap/WeakSet hold 'weak' references to object keys, allowing garbage collection when
no other references exist. WeakMap keys must be objects (not primitives), and they're not iterable/
enumerable. Use cases: storing private data associated with objects without preventing GC, caching
computed values on objects, tracking DOM nodes without memory leaks, and implementing private
class fields polyfills. Unlike Map/Set, they don't prevent memory leaks when objects should be
cleaned up but are still referenced in the collection.

Q16. How does JavaScript handle memory management and what causes memory
leaks? [L4]
Answer: JavaScript uses automatic garbage collection with mark-and-sweep algorithm - it marks
reachable objects from roots (global, stack) and sweeps unreachable ones. Common memory leaks:
forgotten timers/intervals, closures holding large scope references, detached DOM nodes still
referenced in JS, global variables accumulating data, event listeners not removed, and circular
references in older engines. Debugging: Chrome DevTools Memory tab, heap snapshots, allocation
timeline. Prevention: nullify references, use WeakMap/WeakSet, clean up in componentWillUnmount/

Q17. Explain the Proxy object and Reflect API. Provide practical use cases. [L5]
Answer: Proxy wraps objects to intercept/customize fundamental operations (get, set, has,
deleteProperty, etc.) via handler traps. Reflect provides methods matching Proxy traps for performing
default operations. Use cases: validation (reject invalid property assignments), logging/debugging
property access, implementing observable objects for reactivity (Vue 3), auto-populating objects
(default values), access control, creating mock objects for testing, and implementing negative array
indices. Proxies enable meta-programming but have performance overhead. They're non-transpilable,
requiring native support.
Q18. What are the different module systems in JavaScript and how do they differ? [L5]
Answer: CommonJS (CJS): synchronous require(), module.exports, used in Node.js, modules are
cached singletons, dynamic imports possible. ES Modules (ESM): import/export syntax, static
analysis enables tree-shaking, async loading, strict mode by default, live bindings (not copies). AMD:
async browser loading (RequireJS). UMD: universal wrapper for CJS/AMD/global. Key differences:
ESM has static structure (imports hoisted, analyzed at compile time), CJS is dynamic. Node.js
supports both but with different resolution (.mjs/.cjs or package.json type field). Interop requires
special handling.
Q19. Explain Symbol.iterator, Symbol.asyncIterator, and custom iteration protocols.
[L5]
Answer: Symbol.iterator defines an object's default iterator, enabling for...of loops. The method must
return an iterator object with next(). Symbol.asyncIterator is for async iteration with for await...of,
where next() returns Promise<{value, done}>. Custom iteration enables any object to be iterable:
class Range { *[Symbol.iterator]() { for(let i=this.start; i<=this.end; i++) yield i; }}. This powers
generators, spread operator, destructuring, and Array.from(). Async iterables are essential for
streaming data, paginated APIs, and readable streams in Node.js.
Q20. How would you implement a debounce and throttle function? Explain the
differences. [L5]
Answer: Debounce delays execution until after a pause in calls - useful for search input, resize
handlers. Implementation: store timeout, clear on each call, set new timeout. Throttle ensures
execution at most once per interval - useful for scroll handlers, rate limiting. Implementation: track last
execution time, only call if interval elapsed, optionally queue trailing call. Advanced considerations:
leading/trailing edge options, cancel methods, preserving 'this' and arguments, return values via
promises. lodash provides battle-tested implementations. Understanding these patterns is crucial for
performance optimization.

Answer: TypeScript is a typed superset of JavaScript that compiles to plain JavaScript. Benefits

Q2. What are the basic types in TypeScript? [L1]
Answer: TypeScript includes: primitives (string, number, boolean, null, undefined, symbol, bigint),
object types (object, arrays, tuples), special types (any, unknown, never, void), and literal types.
Arrays can be typed as number[] or Array<number>. Tuples are fixed-length arrays with specific types
per position: [string, number]. The 'any' type opts out of type checking, while 'unknown' is the type-
safe counterpart requiring type narrowing before use.
Q3. What is the difference between interface and type alias? [L1]
Answer: Both define object shapes, but interfaces support declaration merging (extending same
interface across files) and are extendable with 'extends'. Type aliases use 'type' keyword and support
unions, intersections, and mapped types more naturally. Interfaces are generally preferred for object
shapes and public APIs due to better error messages. Type aliases are preferred for unions, complex
types, and function types. In modern TypeScript, they're largely interchangeable for object types.
Q4. How do you define optional and readonly properties? [L1]
Answer: Optional properties use ? after the property name: { name?: string } means name can be
string or undefined. Readonly properties use the readonly modifier: { readonly id: number } prevents
reassignment after initialization. You can also use Readonly<T> utility type to make all properties
readonly. For arrays, use ReadonlyArray<T> or readonly T[]. These modifiers help enforce
immutability and document which properties are required for object construction.
Q5. Explain union and intersection types with examples. [L2]
Answer: Union types (|) represent values that can be one of several types: string | number accepts
either. Intersection types (&) combine multiple types into one: TypeA & TypeB has all properties from
both. Example: type Result = Success | Failure for handling outcomes; type AdminUser = User &
{ permissions: string[] } for extending types. Unions require type narrowing (if checks, typeof,
instanceof) to access type-specific properties. Intersections are useful for mixins and combining
interfaces.
Q6. What are generics and why are they useful? [L2]
Answer: Generics allow creating reusable components that work with multiple types while
maintaining type safety. Instead of using 'any', generics preserve type information: function
identity<T>(arg: T): T returns the same type passed in. Common uses: Array<T>, Promise<T>,
Map<K, V>. You can constrain generics: <T extends HasLength> ensures T has a length property.
Generics enable type-safe collections, utility functions, and libraries without sacrificing type
information.

Q8. Explain type narrowing and type guards. [L2]
Answer: Type narrowing refines a union type to a specific type within a code block. Built-in guards:

Narrowing enables safe property access on unions. TypeScript tracks control flow, so after an if
check, the type is narrowed in that branch. Discriminated unions use a common property to narrow

Readonly<T> makes all readonly, Record<K, V> creates object type with keys K and values V.

Q10. Explain conditional types and the infer keyword. [L3]
Answer: Conditional types select types based on conditions: T extends U ? X : Y. The 'infer' keyword
extracts types within the condition: type ReturnType<T> = T extends (...args: any[]) => infer R ? R :
never extracts the return type. Conditional types distribute over unions by default. Practical uses:
unwrapping Promise types, extracting function parameter types, creating type-level if/else logic. They
enable powerful type transformations and are fundamental to many utility types in TypeScript's
standard library.
Q11. What is the difference between unknown and any? When should you use each?
[L3]
Answer: 'any' disables type checking entirely - any operation is allowed, providing no safety.
'unknown' is type-safe: you can't perform operations without first narrowing the type. Use 'unknown'
for values of uncertain type (API responses, user input) - it forces validation before use. Use 'any'
sparingly: migrating JS code, third-party types that are wrong, or truly dynamic scenarios. Prefer
'unknown' for safety; it makes you explicitly handle type uncertainty. Consider using generics or

Q12. How do you handle null and undefined in TypeScript? Explain strict null checks.
[L3]

carefully). Type guards narrow nullable types. This strictness prevents null reference errors at compile

Q15. How does TypeScript's structural typing differ from nominal typing? [L4]
Answer: TypeScript uses structural typing (duck typing): types are compatible if their structures
match, regardless of declared names. If two interfaces have the same properties, they're

compatible. Benefits: flexibility, easier integration with JavaScript. Drawbacks: accidental compatibility.

Q4. What are callbacks and why is callback hell a problem? [L1]
Answer: Callbacks are functions passed as arguments to be executed after an async operation
completes. They were Node.js's original async pattern: fs.readFile(path, (err, data) => { }). Callback
hell occurs when multiple async operations are nested, creating deeply indented code that's hard to
read, maintain, and debug. It also makes error handling verbose - each callback needs its own error
check. Modern solutions include Promises, async/await, and utilities like util.promisify() to convert
callback-based APIs.
Q5. Explain the event loop phases in Node.js. [L2]
Answer: The Node.js event loop has phases executed in order: 1) Timers - execute setTimeout/
setInterval callbacks, 2) Pending callbacks - I/O callbacks deferred from previous iteration, 3) Idle/
Prepare - internal use, 4) Poll - retrieve new I/O events, execute I/O callbacks, 5) Check - execute
setImmediate() callbacks, 6) Close callbacks - socket.on('close'). Between phases, process.nextTick()
and Promise microtasks are processed. Understanding this helps predict execution order and
optimize performance.
Q6. What is the Buffer class and when would you use it? [L2]
Answer: Buffer represents fixed-length sequences of bytes, used for binary data in Node.js. Use
cases: reading files in binary mode, handling network protocols, working with cryptography,
processing images/audio. Creation: Buffer.alloc(size), Buffer.from(string/array). Unlike strings, Buffers
are mutable. Methods include toString(), slice(), copy(), compare(). Important: Buffer.allocUnsafe() is
faster but may contain old memory data. Buffers exist outside V8's heap, managed by Node.js,
essential for performance with large binary data.
Q7. How do you handle errors in Node.js? Explain error-first callbacks. [L2]
Answer: Error-first callback convention: first parameter is error (null if success), second is result.
Always check error first: fs.readFile(path, (err, data) => { if (err) return handleError(err); }). For
Promises, use .catch() or try/catch with async/await. Unhandled errors: use
process.on('uncaughtException') and process.on('unhandledRejection') for logging/cleanup, but exit
the process - don't continue in undefined state. For Express/HTTP servers, use error-handling
middleware. Domain module is deprecated.

Q10. What is the difference between process.nextTick() and setImmediate()? [L3]
Answer: process.nextTick() executes callback after current operation, before the event loop
continues - it's processed in the microtask queue, even before Promises. setImmediate() executes in
the Check phase, after I/O events. nextTick has higher priority and can starve the event loop if used
recursively. Use nextTick for: ensuring callbacks are async, running something after current code but
before I/O. Use setImmediate for: breaking up CPU-intensive work, yielding to event loop. Generally
prefer setImmediate to avoid blocking I/O.
Q11. How do you debug memory leaks in Node.js applications? [L3]

Q12. Explain the cluster module. How does it help with scaling? [L3]
Answer: The cluster module enables running multiple Node.js instances sharing the same port,

(process.send/process.on('message')). Benefits: better CPU utilization, graceful restarts (rolling
deploys), fault tolerance (respawn crashed workers). Limitations: workers don't share memory (use

Q13. What are worker threads and how do they differ from child processes? [L4]
Answer: Worker threads (worker_threads module) run JavaScript in parallel threads sharing memory
via SharedArrayBuffer and transferable objects. Child processes (child_process module) are separate
OS processes with isolated memory. Workers are lightweight - lower overhead for spawning, efficient
data sharing, but share the same libuv thread pool. Child processes provide complete isolation, can
run non-JS executables, and are better for untrusted code. Use workers for CPU-intensive JavaScript
(image processing, parsing). Use child processes for shell commands or when isolation is required.
Q14. Explain libuv and its role in Node.js architecture. [L4]

event loop implementation, async file operations (via thread pool), async DNS resolution, network
operations (epoll/kqueue/IOCP), child process management, and timers. The thread pool (default 4
threads, configurable via UV_THREADPOOL_SIZE) handles blocking operations like file I/O and
crypto. Understanding libuv explains why file operations don't scale like network I/O (thread pool
limits) and helps optimize applications.
Q15. How does Node.js handle backpressure in streams? [L4]

handling: check write() return value, pause readable, resume on drain. Without proper handling,
memory grows unbounded. This is critical for file uploads, proxy servers, and data pipelines. Proper
backpressure ensures stable memory usage regardless of speed differences.

Q18. Explain the V8 garbage collector and how to optimize for it in Node.js. [L5]

Q1. What is PostgreSQL and how does it differ from other databases? [L1]
Answer: PostgreSQL is an open-source, object-relational database known for standards compliance,
extensibility, and advanced features. Compared to MySQL: better JSON support, more complex
query capabilities, stricter SQL compliance, and superior concurrency (MVCC). Unlike NoSQL
databases, it enforces ACID properties and schema constraints. PostgreSQL offers: arrays, JSONB,
full-text search, geographic data (PostGIS), custom types, and stored procedures. It's ideal for
complex queries, data integrity requirements, and applications needing both relational and document-
style storage.
Q2. Explain primary keys, foreign keys, and basic constraints. [L1]
Answer: Primary key uniquely identifies each row - must be unique and NOT NULL, typically auto-
incrementing ID or UUID. Foreign key creates relationships between tables, referencing another
table's primary key, enforcing referential integrity. Constraints: NOT NULL (value required), UNIQUE
(no duplicates), CHECK (custom condition), DEFAULT (fallback value). Example: CREATE TABLE
orders (id SERIAL PRIMARY KEY, user_id INT REFERENCES users(id), status VARCHAR CHECK
(status IN ('pending', 'completed'))). Constraints prevent invalid data at the database level.
Q3. What are the basic SQL operations (SELECT, INSERT, UPDATE, DELETE)? [L1]
Answer: SELECT retrieves data: SELECT columns FROM table WHERE condition ORDER BY
column LIMIT n. INSERT adds rows: INSERT INTO table (columns) VALUES (values). UPDATE
modifies existing rows: UPDATE table SET column = value WHERE condition. DELETE removes
rows: DELETE FROM table WHERE condition. Always use WHERE with UPDATE/DELETE to avoid
affecting all rows. SELECT can include: JOINs for combining tables, GROUP BY for aggregation,
HAVING for filtering groups. These CRUD operations form the foundation of database interaction.
Q4. What is the difference between WHERE and HAVING clauses? [L1]
Answer: WHERE filters individual rows before grouping: SELECT * FROM orders WHERE amount >
100. HAVING filters groups after GROUP BY aggregation: SELECT user_id, SUM(amount) FROM
orders GROUP BY user_id HAVING SUM(amount) > 1000. WHERE cannot use aggregate functions
(SUM, COUNT, AVG), while HAVING can. Execution order: WHERE filters first, then GROUP BY
aggregates, then HAVING filters groups. Use WHERE for row-level conditions, HAVING for aggregate
conditions.
Q5. Explain different types of JOINs and when to use each. [L2]
Answer: INNER JOIN returns only matching rows from both tables. LEFT JOIN returns all rows from
left table plus matches from right (NULL if no match). RIGHT JOIN is opposite - all from right,
matches from left. FULL OUTER JOIN returns all rows from both tables with NULLs where no match.
CROSS JOIN produces cartesian product (every combination). Use INNER for required relationships,
LEFT for optional relationships (show users with or without orders), FULL OUTER for finding
unmatched records on both sides.
Q6. What are indexes and why are they important? [L2]
Answer: Indexes are data structures (usually B-tree) that speed up data retrieval by avoiding full
table scans. Create with: CREATE INDEX idx_name ON table(column). Types: B-tree (default,
comparisons), Hash (equality), GIN (arrays, JSONB, full-text), GiST (geometric, range types). Index
WHERE clause columns, JOIN columns, and ORDER BY columns. Trade-offs: faster reads, slower
writes (index maintenance), storage space. Don't over-index - analyze query patterns. Use EXPLAIN
ANALYZE to verify index usage.

Q7. How do you use transactions in PostgreSQL? [L2]
Answer: Transactions group operations into atomic units - all succeed or all fail. Syntax: BEGIN;
operations; COMMIT; or ROLLBACK;. ACID properties: Atomicity (all-or-nothing), Consistency (valid
state), Isolation (concurrent transaction handling), Durability (committed data persists). Set isolation
levels: SET TRANSACTION ISOLATION LEVEL (READ COMMITTED default, REPEATABLE READ,
SERIALIZABLE). Savepoints allow partial rollbacks: SAVEPOINT name; ROLLBACK TO name;.
Always use transactions for multi-statement operations affecting data integrity.
Q8. Explain aggregate functions and GROUP BY. [L2]
Answer: Aggregate functions compute single results from multiple rows: COUNT (rows), SUM (total),
AVG (average), MIN/MAX (extremes), ARRAY_AGG (collect into array), STRING_AGG (concatenate
strings). GROUP BY groups rows sharing column values for aggregation: SELECT category,
COUNT(*), AVG(price) FROM products GROUP BY category. Multiple columns: GROUP BY
category, status. Non-aggregated SELECT columns must be in GROUP BY. Use HAVING to filter
aggregated results. ROLLUP and CUBE provide subtotals and cross-tabulation.
Q9. How do you read and optimize query execution plans using EXPLAIN? [L3]
Answer: EXPLAIN shows query plan without executing; EXPLAIN ANALYZE executes and shows
actual times. Key elements: Seq Scan (full table scan - often slow), Index Scan (uses index), Nested
Loop/Hash Join/Merge Join (join strategies), cost estimates, rows estimates. Red flags: sequential
scans on large tables, high estimated vs actual rows mismatch, sorts without indexes. Optimization:
add missing indexes, rewrite queries (avoid SELECT *, use specific columns), update statistics
(ANALYZE), consider query restructuring. Compare plans before/after changes.
Q10. What are window functions and when would you use them? [L3]
Answer: Window functions compute values across related rows without collapsing results like
GROUP BY. Syntax: function() OVER (PARTITION BY col ORDER BY col). Common functions:
ROW_NUMBER (unique sequential), RANK/DENSE_RANK (ranking with ties), LAG/LEAD (access
previous/next rows), SUM/AVG OVER (running totals). Use cases: ranking within groups, running
totals, comparing to previous row, moving averages. Example: SELECT *, ROW_NUMBER() OVER
(PARTITION BY department ORDER BY salary DESC) as rank FROM employees - ranks employees
within each department.
Q11. How do you handle JSONB data in PostgreSQL? [L3]

Q12. Explain normalization and when you might denormalize. [L3]
Answer: Normalization reduces data redundancy through forms: 1NF (atomic values, unique rows),
2NF (no partial dependencies), 3NF (no transitive dependencies). Benefits: data integrity, smaller
storage, easier updates. Denormalization intentionally adds redundancy for read performance: storing

complex joins causing performance issues, reporting/analytics tables. Strategy: normalize first,
denormalize specific cases based on measured performance needs. Consider materialized views as
middle ground.

Q1. What is MongoDB and how does it differ from relational databases? [L1]
Answer: MongoDB is a NoSQL document database storing data as flexible JSON-like documents
(BSON). Unlike relational databases with fixed schemas and tables, MongoDB offers: flexible schema
(documents can have different fields), embedded documents (denormalized data), horizontal scaling
(sharding), and natural mapping to programming objects. Trade-offs: less strict data integrity (no
foreign keys by default), eventual consistency options, different query paradigm. MongoDB suits
applications with evolving schemas, hierarchical data, and high write volumes.
Q2. Explain the basic structure: databases, collections, and documents. [L1]
Answer: MongoDB organizes data hierarchically: databases contain collections, collections contain
documents. A document is a BSON (Binary JSON) object with field-value pairs, equivalent to a row in
SQL. Collections are groups of documents, similar to tables but schema-flexible. Documents can
contain nested objects and arrays. Each document has a unique _id field (ObjectId by default).
Example: database 'ecommerce' has collection 'products' containing documents like { _id:
ObjectId(...), name: "Widget", price: 29.99, tags: ["new", "sale"] }.
Q3. What are the basic CRUD operations in MongoDB? [L1]
Answer: Create: insertOne({doc}), insertMany([docs]). Read: find({query}), findOne({query}). Update:
updateOne({filter}, {$set: changes}), updateMany(), replaceOne(). Delete: deleteOne({filter}),
deleteMany({filter}). Find supports projections (field selection), sorting, limit, skip. Update operators:
$set (set field), $unset (remove field), $inc (increment), $push (add to array). Example:
db.users.find({ age: { $gte: 18 } }).sort({ name: 1 }).limit(10) finds adults sorted by name.
Q4. Explain MongoDB query operators and provide examples. [L2]
Answer: Comparison: $eq, $ne, $gt, $gte, $lt, $lte, $in, $nin. Logical: $and, $or, $not, $nor. Element:
$exists, $type. Array: $elemMatch, $all, $size. Example: find users aged 18-30 who are active:
db.users.find({ age: { $gte: 18, $lte: 30 }, status: { $in: ['active', 'pending'] } }). Nested documents:
{ "address.city": "NYC" }. Array queries: { tags: "javascript" } matches if array contains value.
$elemMatch matches array elements meeting multiple conditions.
Q5. How do indexes work in MongoDB and when should you create them? [L2]
Answer: Indexes improve query performance by avoiding collection scans. Create with
createIndex({ field: 1 }) where 1 is ascending, -1 descending. Types: single field, compound (multiple
fields - order matters), multikey (arrays), text (full-text search), geospatial (2d, 2dsphere). Use
explain() to verify index usage. Index: fields in query conditions, sort fields, frequently accessed.
Avoid: over-indexing (write overhead), indexing high-cardinality arrays. Unique indexes enforce
uniqueness. Partial indexes for filtering. Background creation for production.
Q6. What is the aggregation pipeline and how do you use it? [L2]
Answer: Aggregation pipeline processes documents through stages for complex data
transformations. Common stages: $match (filter), $group (aggregate), $project (reshape), $sort,
$limit, $skip, $lookup (join), $unwind (deconstruct arrays). Example: db.orders.aggregate([{ $match:
{ status: "completed" }}, { $group: { _id: "$customerId", total: { $sum: "$amount" }}}]). Stages execute
sequentially - optimize by placing $match early. Expression operators: $sum, $avg, $first, $push.
Aggregation is MongoDB's equivalent to SQL GROUP BY with more flexibility.
Q7. When should you embed documents versus reference them? [L3]

doesn't change independently, read performance is priority. Example: embed addresses in user
documents. Reference (normalize) when: many-to-many relationships, data is accessed
independently, documents would exceed 16MB limit, data changes frequently. Example: reference
products in orders. Hybrid: embed commonly accessed fields, reference full documents. Consider:
query patterns, update frequency, document growth. MongoDB's $lookup enables joins but has
performance implications at scale.

arrays. 5) Plan indexes based on query patterns. Patterns: polymorphic (different document types in
collection), bucket (time-series grouping), computed (pre-aggregate), extended reference (partial
embedding). Avoid: massive arrays, documents approaching 16MB, deep nesting. Test with realistic
data volumes. Schema validation enforces structure where needed.
Q13. How do you handle data consistency and durability in MongoDB? [L5]
Answer: Write concern controls durability: w:1 (primary ack), w:majority (majority ack, survives
primary failure), w:0 (fire-and-forget). Journal: j:true ensures write-ahead log durability. Read concern:
local (latest primary data, may rollback), majority (committed data), linearizable (strongest, reads
reflect all acknowledged writes). For consistency: majority write + majority read = read-your-writes
guarantee. Causal consistency: sessions track operations, ensure causal ordering. Trade-offs:
stronger consistency increases latency. Production: use majority write concern, configure appropriate
timeouts, monitor replication lag.

Q1. What is Redis and what are its common use cases? [L1]

Q3. How do you set and get values with expiration in Redis? [L1]

if not exists), SETXX (set if exists). Common pattern for caching: SET user:123 "data" EX 3600

Q1. What is REST and what are its core principles? [L1]
Answer: REST (Representational State Transfer) is an architectural style for web services. Core
principles:1)Client-Serverseparation(independentevolution).2)Stateless(eachrequestcontainsall

URLs, typically exchanging JSON data.
Q2. Explain HTTP methods and their purposes in REST APIs. [L1]
Answer: GET: retrieve resource(s), idempotent, cacheable, no request body. POST: create new
resource,notidempotent,returns201withlocationheader.PUT:replaceentireresource,idempotent,
returns 200/204. PATCH: partial update, may or may not be idempotent. DELETE: remove resource,

have same effect as single request.
Q3. What are the common HTTP status codes and when do you use them? [L1]
Answer: 2xx Success: 200 OK (general success), 201 Created (resource created), 204 No Content
(success with no body). 3xx Redirection: 301 Moved Permanently, 304 Not Modified (caching). 4xx
Client Error: 400 Bad Request (invalid input), 401 Unauthorized (not authenticated), 403 Forbidden
(authenticated but not allowed), 404 Not Found, 409 Conflict, 422 Unprocessable Entity (validation).
5xx Server Error: 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable. Choose
appropriate codes for clear API communication.
Q4. How do you design RESTful URLs and resource naming? [L2]
Answer: Use nouns for resources, not verbs: /users not /getUsers. Plural for collections: /users,
singular for item: /users/:id. Hierarchical for relationships: /users/:id/orders. Query parameters for
filtering, sorting, pagination: /users?status=active&sort=name&page=2. Avoid deep nesting (max 2-3
levels). Use lowercase, hyphens for multi-word: /order-items. Consistent patterns across API. Actions
that don't fit CRUD: sub-resources /users/:id/activate or POST with action in body.
Q5. How do you implement pagination in REST APIs? [L2]
Answer: Common patterns: 1) Offset pagination: ?page=2&limit=20 or ?offset=20&limit=20. Simple
but poor for large datasets (offset scans). 2) Cursor pagination: ?cursor=abc123&limit=20, returns
next/prev cursors. Better performance, stable for real-time data. 3) Keyset pagination: ?
after_id=100&limit=20, uses indexed column. Response should include: total count (optional,
expensive), links to next/prev/first/last pages, current page info. Link headers or response body
pagination object are common formats.

Q1. What is GraphQL and how does it differ from REST? [L1]
Answer: GraphQL is a query language for APIs with a strongly-typed schema. Key differences from
REST: clients specify exactly which fields they need (no over/under-fetching), single endpoint handles
all operations, nested data in one request (no multiple roundtrips), introspection for self-
documentation. GraphQL uses POST requests with query strings, returns JSON. Trade-offs: more
complex server implementation, caching is harder, potential for expensive queries. Best for: complex
UIs needing flexible data, mobile apps with bandwidth concerns.
Q2. Explain queries, mutations, and subscriptions in GraphQL. [L1]
Answer: Queries: read operations, fetch data without side effects. Example: query { user(id: 1)
{ name, email } }. Mutations: write operations that modify data (create, update, delete). Example:
mutation { createUser(name: "John") { id } }. Subscriptions: real-time updates via WebSocket, server
pushes data when events occur. Example: subscription { messageAdded { content } }. Queries and
mutations are request-response, subscriptions maintain connection. Each operation type can have
multiple operations, executed with operation name.
Q3. What is a GraphQL schema and how do you define types? [L1]
Answer: Schema defines available data and operations using Schema Definition Language (SDL).
Types: Scalar (Int, Float, String, Boolean, ID), Object (custom types with fields), Enum, Input (for
mutation arguments), Interface, Union. Example: type User { id: ID!, name: String!, email: String,
posts: [Post!]! }. Non-null with !, arrays with []. Query and Mutation are special root types. Resolvers
implement data fetching for each field. Schema is the contract between client and server.
Q4. How do resolvers work in GraphQL? [L2]
Answer: Resolvers are functions that return data for schema fields. Signature: (parent, args, context,
info) => data. Parent: result from parent resolver (for nested fields). Args: field arguments. Context:
shared data (auth, database). Info: query AST, field details. Resolvers can be async, return Promises.
Default resolver returns parent[fieldName]. Chain: query resolver returns User, then User.posts
resolver fetches posts. Implementation: organize by type, keep business logic in services, resolvers
coordinate data fetching.
Q5. How do you handle authentication and authorization in GraphQL? [L2]
Answer: Authentication: verify identity in context setup (parse JWT from headers, attach user to
context). All resolvers access context.user. Authorization approaches: 1) Resolver-level: check
permissions in each resolver. 2) Directive-based: @auth directive on schema fields. 3) Middleware/
shield: graphql-shield provides permission layer. Patterns: throw AuthenticationError for
unauthenticated, ForbiddenError for unauthorized. Schema visibility: filter introspection based on
roles. Consider: field-level vs type-level permissions, row-level security for data filtering.
Q6. What are GraphQL fragments and when would you use them? [L2]
Answer: Fragments are reusable field selections. Define once, use in multiple queries: fragment
UserFields on User { id, name, email }. Use with spread: query { user(id: 1) { ...UserFields } }.
Benefits: DRY (avoid repeating field lists), maintainability (update in one place), conditional fields with
inline fragments (... on Admin { permissions }). Client-side: used extensively in React/Apollo for
component data requirements. Fragments enable composition and co-location of data requirements
with components.

Q1. What is the difference between authentication and authorization? [L1]
Answer: Authentication verifies identity - "who are you?" Proves user is who they claim to be through
credentials (password, token, biometrics). Authorization determines permissions - "what can you do?"
After authentication, checks if user has access to specific resources or actions. Example: logging in is
authentication; checking if user can delete a post is authorization. Both are required for secure
systems - authenticate first, then authorize for each action.
Q2. What is JWT and what are its components? [L1]
Answer: JWT (JSON Web Token) is a compact, URL-safe token format for securely transmitting
claims. Three parts separated by dots: Header (type and algorithm, base64), Payload (claims - user
data, expiration, base64), Signature (header + payload signed with secret). Example:
xxxxx.yyyyy.zzzzz. Common claims: sub (subject/user ID), exp (expiration), iat (issued at), iss

(issuer). Server verifies signature to trust claims without database lookup. JWTs are not encrypted by
default - don't store sensitive data in payload.
Q3. How do sessions differ from token-based authentication? [L1]
Answer: Sessions: server stores session data, client holds session ID cookie. Server looks up
session on each request. Stateful - requires session storage. Logout invalidates server-side session.
Tokens (JWT): client holds complete token with claims. Server verifies signature, no lookup needed.
Stateless - scales horizontally easily. Harder to invalidate before expiration. Sessions: simpler
revocation, server memory/storage. Tokens: better for APIs, microservices, mobile apps. Many
systems use both - short-lived JWT with session-backed refresh tokens.
Q4. How do you implement JWT authentication in a Node.js application? [L2]
Answer: Login endpoint: verify credentials, create token with jsonwebtoken: jwt.sign({ userId },
secret, { expiresIn: '1h' }). Return token to client. Client: store token (memory, httpOnly cookie), send
in Authorization header: Bearer <token>. Middleware: extract token, jwt.verify(token, secret), attach
user to request. Protect routes: apply auth middleware. Handle errors: token expired (401), invalid
token (401). Considerations: use environment variable for secret, short expiration, secure token
transmission (HTTPS).
Q5. What is a refresh token and why is it needed? [L2]
Answer: Refresh tokens allow obtaining new access tokens without re-authentication. Access tokens:
short-lived (15min-1hr), sent with every request, if stolen limited damage window. Refresh tokens:
long-lived (days/weeks), stored securely (httpOnly cookie), only sent to refresh endpoint, can be
revoked. Flow: access token expires, client uses refresh token to get new access token. Benefits:
balance security (short access) with UX (don't re-login frequently). Store refresh tokens in database
for revocation capability.

Q7. Explain OAuth 2.0 and its common flows. [L3]

Q1. What is Git and why is version control important? [L1]
Answer: Git is a distributed version control system tracking changes in source code. Benefits:
complete history of changes with ability to revert, parallel development via branching, collaboration
without overwriting others' work, backup across multiple locations, accountability through commit
attribution. Distributed means each developer has full repository copy, enabling offline work and
redundancy. Git tracks content changes efficiently using snapshots and SHA-1 hashes, making it fast

Q2. Explain the basic Git workflow: add, commit, push, pull. [L1]
Answer: git add stages changes for commit (from working directory to staging area). git commit
saves staged changes to local repository with a message describing the change. git push uploads
local commits to remote repository (GitHub, GitLab). git pull fetches and merges remote changes into
local branch. Workflow: make changes, git add files, git commit -m "message", git push origin branch.
Pull before pushing to incorporate others' changes. This enables tracking work, sharing with team,
and maintaining history.
Q3. What is a branch and why would you create one? [L1]
Answer: A branch is an independent line of development, a pointer to a specific commit. Branches
allow: working on features without affecting main code, multiple parallel workstreams, experimenting
safely (can discard branch), isolating bug fixes. Commands: git branch name (create), git checkout
name or git switch name (switch), git checkout -b name (create and switch), git merge name (merge
into current). Common branches: main/master (production), develop (integration), feature branches,
hotfix branches.
Q4. How do you resolve a merge conflict? [L1]
Answer: Merge conflicts occur when Git can't automatically combine changes (same lines modified
differently). Git marks conflicts in files with <<<<<<<, =======, >>>>>>> markers. Resolution: open
conflicted files, decide which changes to keep (or combine both), remove conflict markers, git add
resolved files, complete merge with git commit. Tools: VS Code has built-in conflict resolution, git
mergetool opens configured diff tool. Prevention: communicate with team, pull frequently, smaller
focused commits, avoid long-lived branches.
Q5. Explain the difference between merge and rebase. [L2]
Answer: Merge creates a new commit combining two branches, preserving complete history with
merge commit. Rebase replays commits from current branch onto target branch, creating linear
history without merge commits. Use merge for: public/shared branches, preserving context of feature
development. Use rebase for: cleaning up local commits before push, keeping linear history. Golden
rule: never rebase public branches (rewrites history others may have). Interactive rebase (git rebase -
i) allows squashing, editing, reordering commits before sharing.
Q6. How do you undo changes in Git? Explain reset, revert, and checkout. [L2]
Answer: git checkout file discards working directory changes (pre-commit). git reset HEAD file
unstages changes. git reset --soft HEAD~1 undoes last commit, keeps changes staged. git reset --
mixed HEAD~1 (default) undoes commit and unstaging. git reset --hard HEAD~1 discards commit
and all changes completely. git revert commit creates new commit undoing specified commit (safe for
shared history). Use reset for local unpushed commits, revert for pushed commits. git stash
temporarily stores uncommitted changes.

Q1. What is a message queue and why would you use one? [L1]
Answer: A message queue is middleware that enables asynchronous communication between
services. Producers send messages to the queue, consumers process them independently. Benefits:
decoupling (services don't need direct connections), resilience (queue buffers messages if consumer
is down), scalability (add more consumers), load leveling (handle traffic spikes). Use cases: email
sending, payment processing, data pipelines, microservice communication. Popular options:
RabbitMQ, Amazon SQS, Redis queues, Apache Kafka.
Q2. What is the difference between a message queue and pub/sub? [L1]
Answer: Message queue: point-to-point delivery, each message consumed by one consumer, work
distribution. Pub/Sub: one-to-many, message sent to all subscribers, event broadcasting. Queue: task
processing (email sending, order processing). Pub/Sub: notifications, real-time updates, event
distribution. Some systems offer both: RabbitMQ exchanges for pub/sub, Kafka consumer groups for
queue behavior. Choose based on: does each message need one processor (queue) or should
multiple services react (pub/sub)?
Q3. What are producers and consumers in messaging systems? [L1]
Answer: Producers create and send messages to queues/topics. They don't wait for processing, just
confirm message is queued. Consumers receive and process messages from queues. In queue
model: messages are distributed among consumers (competing consumers pattern). In pub/sub:
each subscriber gets every message. Consumer acknowledges (ack) successful processing; unacked
messages are requeued. Multiple consumers can process queue in parallel for higher throughput.
Producers and consumers are decoupled - they can be different services, scale independently.
Q4. How do you implement a job queue in Node.js? [L2]
Answer: Popular libraries: Bull (Redis-based), BullMQ (modern rewrite), Agenda (MongoDB-based),
Bee-Queue. Example with Bull: const queue = new Bull('email'); queue.add({ email, subject, body });
queue.process(async (job) => { await sendEmail(job.data); }). Features: job retries, delayed jobs, rate
limiting, job priority, progress tracking. Workers can run in separate processes for CPU-intensive
work. Consider: job serialization limits, Redis availability, idempotent job processing. Dashboard: Bull
Board for monitoring.
Q5. How do you handle message acknowledgment and retries? [L2]
Answer: Acknowledgment confirms successful processing. Auto-ack: message removed when
received (may lose on crash). Manual ack: consumer explicitly acknowledges after processing (safer).
On failure: nack/reject returns message to queue for retry. Retry strategies: immediate, exponential
backoff, max retries then dead-letter queue. Dead-letter queue (DLQ): stores failed messages for
investigation. Implementation: wrap processing in try-catch, ack on success, nack on error. Configure:
max retry count, backoff delays, DLQ routing. Monitor DLQ for recurring failures.
Q6. What is message ordering and why does it matter? [L2]
Answer: Ordering: processing messages in the sequence they were sent. Important for: event
sourcing (events must replay in order), financial transactions, sequential workflows. Challenges:
parallel consumers break ordering, retries can reorder, partitioning distributes messages. Solutions:
single consumer per queue (limits throughput), partition by key (Kafka, SQS FIFO), sequence
numbers in messages. FIFO queues: Amazon SQS FIFO, RabbitMQ with single consumer. Trade-off:
ordering often conflicts with parallelism and scalability. Design: do you truly need strict ordering?

Q7. How do you ensure exactly-once message processing? [L3]
Answer: Delivery guarantees: at-most-once (may lose), at-least-once (may duplicate), exactly-once

### Modern React Component Example
```tsx
// Modern React component with performance optimization
import React, { memo, useCallback, useMemo } from 'react';
import { useVirtualizer } from '@tanstack/react-virtual';

interface DataTableProps {
  data: Array<Record<string, any>>;
  columns: Column[];
  onRowClick?: (row: any) => void;
}

export const DataTable = memo<DataTableProps>(({ data, columns, onRowClick }) => {
  const parentRef = React.useRef<HTMLDivElement>(null);
  
  const rowVirtualizer = useVirtualizer({
    count: data.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 50,
    overscan: 5,
  });

  const handleRowClick = useCallback((row: any) => {
    onRowClick?.(row);
  }, [onRowClick]);

  return (
    <div
      ref={parentRef}
      className="h-96 overflow-auto"
      role="table"
      aria-label="Data table"
    >
      {rowVirtualizer.getVirtualItems().map((virtualItem) => {
        const row = data[virtualItem.index];
        return (
          <div
            key={virtualItem.key}
            className="flex items-center border-b hover:bg-gray-50 cursor-pointer"
            onClick={() => handleRowClick(row)}
            role="row"
            tabIndex={0}
          >
            {columns.map((column) => (
              <div key={column.key} className="px-4 py-2 flex-1" role="cell">
                {row[column.key]}
              </div>
            ))}
          </div>
        );
      })}
    </div>
  );
});
```
